# LAW.db 재설계 — 한국 법률 체계를 이해하는 데 필요한 것만, 함정 없는 모양으로

## Context

`LAW.db`(3.96GB, 표 18·뷰 12)는 법제처 API 여섯 자료종류를 1:1로 담아 온 결과라, 목적("한국 법률 체계를 깊이 이해한다")과 관계가 적은 자료(행정규칙 본문·부칙·행정심판례·항호목 분해)와 수집기 내부 원장 5표, 판본 함정을 가리려고 생긴 뷰 4개가 클로드가 필요한 표를 찾는 시야를 가린다. 브리프 `.tmp/user inputs/260912_law db 개선.md`가 이 재설계를 요청했고, 앞선 계획 `260912_DB 재분할.md`가 "표·컬럼·뷰 설계와 원장 5표 접기"를 이 계획(#2)으로 미뤄 두었다.

이 계획은 2026-09-12 계획 세션에서 실측(sqlite 집계)과 사용자 결정으로 확정한 것이다. 결정의 근거 수치는 이 파일의 "실측 대장"에 있고, 스키마 주석에는 넣지 않는다(`tests/주석수치.py`).

목표 한 문장: **클로드가 법령·판례·헌재결정·법제처해석을 SQL로 좁혀 읽을 때, 표 이름만 보고 어디를 볼지 알고, 필터를 빼먹어도 틀린 수가 나오지 않는 DB.**

## 새 스키마 (Scripts/law/schema.py 의 SCHEMA 전문)

주석 규율은 기존 그대로다: 표·뷰 머리 첫 줄은 "무엇 하나가 한 행인가 + 가장 큰 함정", 한 주장은 한 줄, `⚠`는 줄에 하나, 실측 수치·관리자 좌표 없음, 교차 참조는 백틱, NULL의 뜻은 질의를 바꿀 때만.

```sql
CREATE TABLE IF NOT EXISTS 법령 (
  -- 현행 법령 하나가 한 행이다. 판본이 아니라 법이 행이므로 같은 법이 두 번 세어지지 않는다.
  -- 담는 판본은 원천이 현행으로 분류한 것이다. 현행 판본이 없는 법(제정 후 시행 전 등)은 시행예정 분류 판본 중 시행일이 오늘 뒤인 가장 이른 것, 그것도 없으면 가장 늦은 것을 담는다.
  -- 이미 공포된 다음 판본이 있으면 시행예정일련번호가 가리키며 그 판본의 조문은 여기 없다. 개정 전후 대조는 `direct.py 신구법`, 과거 판본은 `direct.py 연혁본문`이다.
  -- 날짜는 'YYYY-MM-DD'다. 'YYYYMMDD'와 비교하면 에러 없이 틀린 범위가 나온다. 빈 컬럼은 원천이 주지 않은 것이다.
  법령ID       TEXT NOT NULL PRIMARY KEY,  -- 법 자체의 원천 식별자로 개정돼도 유지된다. `조문`·`위임`·`의율조문`이 이 키로 잇는다.
  법령일련번호 TEXT NOT NULL UNIQUE,  -- 담긴 판본의 원천 MST로 `direct.py`가 받는 손잡이다. 개정 판본마다 새로 발급된다.
  법령명       TEXT NOT NULL,
  법령약칭     TEXT,  -- 판례가 인용하는 약칭이다.
  법종구분     TEXT NOT NULL,  -- 예: '법률'·'대통령령'·'국토교통부령'. 시행령·시행규칙도 이 표의 행이며 법과의 관계는 `위임`에 있다.
  소관부처     TEXT,
  공포일자     TEXT,
  공포번호     TEXT,  -- 판례의 '법률 제N호로 개정' 인용과 이어지도록 앞자리 0을 보존한 문자열이다.
  시행일자     TEXT,  -- 이 판본에서 가장 늦게 시행되는 조항의 시행일이다. 오늘 뒤여도 나머지 조항은 시행 중일 수 있으며 조별 시행일은 `조문.시행일자`다.
  제개정구분   TEXT,  -- 예: '제정'·'일부개정'·'전부개정'·'타법개정'.
  개정문       TEXT,  -- 이 판본을 만든 개정의 개정문이다.
  제개정이유   TEXT,  -- 입법 취지다.
  시행예정일련번호 TEXT,  -- 공포됐으나 아직 시행 전인 다음 판본의 MST다. NULL은 그런 판본이 없다는 뜻이다.
  시행예정일   TEXT,  -- 그 판본의 시행일이다. 예정 판본이 여럿이면 가장 이른 것이다.
  수집일시     TEXT NOT NULL,  -- 이 행을 받은 로컬 시각이며 원천 수정시각이 아니다.
  위임수집판본 TEXT,  -- `위임`을 받았을 때의 MST다. NULL이거나 법령일련번호와 다르면 `위임` 0행은 위임 없음이 아니라 미수집이다.
  CHECK ((시행예정일련번호 IS NULL) = (시행예정일 IS NULL))
);
CREATE INDEX IF NOT EXISTS idx_법령_명   ON 법령(법령명);
CREATE INDEX IF NOT EXISTS idx_법령_부처 ON 법령(소관부처);

CREATE TABLE IF NOT EXISTS 조문 (
  -- 현행 법령의 조 하나가 한 행이다. 법령 조회의 진입점이며 목차는 편장절, 본문은 전문이다.
  -- 항·호·목은 전문 안에 원천 순서대로 펼쳐져 있다. 항 하나만 떼어 읽으면 앞 항을 가리키는 문맥이 끊기므로 조 단위로 읽는다.
  법령ID   TEXT NOT NULL REFERENCES 법령(법령ID) ON DELETE CASCADE,
  순서     INTEGER NOT NULL,  -- 원천 배열 순서다. 조 번호 순과 다를 수 있어 본문 순서 복원은 이것이다.
  조       INTEGER NOT NULL,
  가지     INTEGER NOT NULL DEFAULT 0,  -- 제7조와 제7조의2는 조=7을 공유하고 가지 0과 2로 갈린다. 조만 걸면 둘이 함께 온다.
  편장절   TEXT,  -- 이 조가 속한 편·장·절 제목을 '>'로 이은 경로다. NULL은 편·장·절 구분이 없는 법령이다.
  제목     TEXT,
  전문     TEXT NOT NULL,  -- 조 머리와 모든 항·호·목을 이어 붙인 본문이다.
  시행일자 TEXT,  -- 조 단위 시행일로 `법령.시행일자`와 다를 수 있다.
  변경여부 TEXT,  -- 원천 'Y'는 이 판본에서 바뀐 조의 후보 표지이며 효력 확정값이 아니다.
  PRIMARY KEY (법령ID, 순서)
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_조문_좌표 ON 조문(법령ID, 조, 가지);

CREATE TABLE IF NOT EXISTS 위임 (
  -- 법 조문이 시행령·시행규칙에 위임한 관계 하나가 한 행이다. 조문에서 대상 규범으로 향하며 대상 본문은 `위임대상조문`에 있다.
  -- 다른 법을 끌어 쓴 인용 관계·자치법규·행정규칙 위임은 담지 않는다. 인용은 조문 전문의 「법령명」을 LIKE로 찾고 행정규칙은 `direct.py`다.
  -- ⚠ 위임구분 '시행령'에는 다른 대통령령이 섞인다. 자기 시행령만 필요하면 대상법령ID나 정확한 이름으로 좁힌다.
  법령ID     TEXT NOT NULL REFERENCES 법령(법령ID) ON DELETE CASCADE,
  순서       INTEGER NOT NULL,
  조         INTEGER NOT NULL,  -- 위임한 원 법령의 조다.
  가지       INTEGER NOT NULL DEFAULT 0,
  위임한자리 TEXT,  -- 원천 조항호목 문자열로 예: '제2조제6호나목'.
  위임구분   TEXT NOT NULL CHECK (위임구분 IN ('시행령','시행규칙')),
  대상제목   TEXT,  -- 대상 규범의 이름이다.
  대상법령ID TEXT,  -- 대상제목을 현행 법령명에 맞춘 결과다. NULL은 매칭 실패이며 위임 부재가 아니다.
  대상조     INTEGER,  -- NULL은 원천이 대상 조를 주지 않은 관계다.
  대상가지   INTEGER NOT NULL DEFAULT 0,
  근거문구   TEXT,
  PRIMARY KEY (법령ID, 순서)
);
CREATE INDEX IF NOT EXISTS idx_위임_대상 ON 위임(대상법령ID, 대상조, 대상가지);

CREATE TABLE IF NOT EXISTS 판례 (
  -- 대법원 출처에서 수집한 판례 하나가 한 행이다. 하급심도 원천이 선별한 범위에서 들어 있다.
  -- ⚠ 검색 결과 없음은 이 수집 범위와 조건에서 못 찾았다는 뜻이며 판례 부재가 아니다. 빈 컬럼은 원천이 주지 않은 것이다.
  판례ID   TEXT NOT NULL PRIMARY KEY,  -- 원천 일련번호이며 law.go.kr 링크의 손잡이다. `의율조문`·`인용판례`의 자료ID가 이 값이다.
  사건번호 TEXT NOT NULL,  -- 인용에 쓰는 공개 번호다. 같은 사건번호의 행이 여럿일 수 있어 조인 키가 아니다.
  사건명   TEXT,
  법원명   TEXT,  -- 정규화한 정식 명칭이다. 옛 법원과 후신은 합치지 않는다.
  선고일자 TEXT,
  형식     TEXT CHECK (형식 IN ('판결','결정','명령','심판')),  -- NULL은 원천 표기를 분류하지 못한 것이다.
  전원합의체 INTEGER NOT NULL DEFAULT 0 CHECK (전원합의체 IN (0,1)),  -- 1은 대법원 전원합의체 재판이다. 판례 변경의 표지로 본문에 그 말이 없어도 이 값이 근거다.
  사건종류 TEXT,  -- 예: '민사'·'형사'·'일반행정'·'세무'·'특허'·'가사'.
  판시사항 TEXT,  -- 쟁점별 법리 요약이다. 사실관계는 판례내용에 있다.
  판결요지 TEXT,
  참조조문 TEXT,  -- 쟁점별 참조 조문 원문으로 예: '[1] 민법 제109조 / [2] …'. 조 좌표로 푼 것이 `의율조문`이다. NULL은 본문에 조문이 없다는 뜻이 아니다.
  참조판례 TEXT,  -- 쟁점별 선례 인용 원문으로 푼 것이 `인용판례`다.
  판례내용 TEXT,  -- 전문이다.
  수집일시 TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_판례_사건번호 ON 판례(사건번호);
CREATE INDEX IF NOT EXISTS idx_판례_선고일   ON 판례(선고일자);
CREATE INDEX IF NOT EXISTS idx_판례_법원     ON 판례(법원명, 선고일자);

CREATE TABLE IF NOT EXISTS 헌재결정례 (

DROP VIEW IF EXISTS 위임대상조문;
CREATE VIEW 위임대상조문 AS
  -- 법 조문 하나가 시행령·시행규칙에 위임한 관계 하나가 한 행이며 대상 조문 본문을 붙인다. 대상 미해결 관계도 남긴다.
  -- ⚠ 대상전문 NULL은 대상 법령 미매칭·조 미제공·조 부존재로 본문을 못 붙였다는 뜻이며 위임 부재가 아니다.
  SELECT 원.법령ID, 원.법령명, y.조, y.가지, y.위임한자리, y.위임구분, y.근거문구, y.대상제목,
         대.법령ID AS 대상법령ID, 대.법령명 AS 대상법령명, y.대상조, y.대상가지,
         j.제목 AS 대상조제목, j.전문 AS 대상전문
    FROM 위임 y
    JOIN 법령 원 ON 원.법령ID = y.법령ID
    LEFT JOIN 법령 대 ON 대.법령ID = y.대상법령ID
    LEFT JOIN 조문 j ON j.법령ID = 대.법령ID AND j.조 = y.대상조 AND j.가지 = y.대상가지;

DROP VIEW IF EXISTS 조문판단;
CREATE VIEW 조문판단 AS
  -- 조 하나를 다룬 판단 하나가 한 행이다. 판례·헌재결정·법제처해석을 한 모양(번호·기관·일자·요지)으로 붙여 자료종류별 조인을 대신한다.
  -- ⚠ 여러 조를 한꺼번에 세면 같은 판단이 조마다 반복된다. 판단 수는 (자료종류, 자료ID)로 센다.
  -- 항·호·쟁점은 접었다. 그 구조와 부칙 참조·미매칭 참조는 `의율조문`에 있다.
  SELECT DISTINCT y.법령ID, y.조, y.가지, y.자료종류, y.자료ID,
         p.사건번호 AS 번호, p.법원명 AS 기관, p.선고일자 AS 일자, p.판시사항 AS 요지
    FROM 의율조문 y JOIN 판례 p ON y.자료종류='판례' AND p.판례ID = y.자료ID
   WHERE y.법령ID IS NOT NULL AND y.조 IS NOT NULL AND y.부칙여부 = 0
  UNION ALL
  SELECT DISTINCT y.법령ID, y.조, y.가지, y.자료종류, y.자료ID,
         d.사건번호, '헌법재판소', d.종국일자, COALESCE(d.판시사항, d.결정요지)
    FROM 의율조문 y JOIN 헌재결정례 d ON y.자료종류='헌재결정례' AND d.헌재결정례ID = y.자료ID
   WHERE y.법령ID IS NOT NULL AND y.조 IS NOT NULL AND y.부칙여부 = 0
  UNION ALL
  SELECT DISTINCT y.법령ID, y.조, y.가지, y.자료종류, y.자료ID,
         h.안건번호, '법제처', h.해석일자, h.회답
    FROM 의율조문 y JOIN 법령해석례 h ON y.자료종류='법령해석례' AND h.법령해석례ID = y.자료ID
   WHERE y.법령ID IS NOT NULL AND y.조 IS NOT NULL AND y.부칙여부 = 0;

DROP VIEW IF EXISTS 조문판단수;
CREATE VIEW 조문판단수 AS
  -- 현행 조 하나가 한 행이며 `조문판단`에 있는 판단을 자료종류별로 센다. 0은 판단 부재가 아니라 매칭 부재다.
  SELECT c.법령ID, l.법령명, c.조, c.가지, c.제목, c.순서,
         COUNT(DISTINCT CASE WHEN y.자료종류='판례'       THEN y.자료ID END) AS 판례수,
         COUNT(DISTINCT CASE WHEN y.자료종류='헌재결정례' THEN y.자료ID END) AS 헌재수,
         COUNT(DISTINCT CASE WHEN y.자료종류='법령해석례' THEN y.자료ID END) AS 해석수
    FROM 조문 c JOIN 법령 l USING (법령ID)
    LEFT JOIN 조문판단 y ON y.법령ID = c.법령ID AND y.조 = c.조 AND y.가지 = c.가지
   GROUP BY c.법령ID, c.순서;

DROP VIEW IF EXISTS 신선도;
CREATE VIEW 신선도 AS
  -- **이 답은 언제 기준인가.** 항상 한 행이다 — 빈 DB 에서도 값이 NULL 인 한 행이 온다.
  -- 사용자가 "지금 어떻게 되어 있나"를 물을 때 그 '지금'이 며칠 전인지 모르면 낡은 시점의 답을 오늘 것인 양 내놓게 된다. 그래서 시점을 묻는 질의는 여기서 끝난다.
  SELECT s.갱신일시 AS 적재기준시각,  -- 마지막 수집 실행이 원천을 받고 끝난 시각(KST). NULL = 받은 기록이 없다.
         CASE WHEN g.상태 IS NULL THEN NULL WHEN g.상태 = '완료' AND COALESCE(g.건수, 0) = 0 THEN 1 ELSE 0 END AS 감사통과,  -- 1 = 게이트를 다 통과. NULL = 감사 기록 없음. **0 = 위반이 남아 있었다** — 이 DB 를 근거로 답할 때는 감사상세의 게이트가 무엇을 재는지 확인하거나, 못 하면 그 한계를 답에 밝힌다.
         g.갱신일시 AS 감사시각,  -- ⚠ **그 감사가 언제 것인가.** 감사는 수집이 돌 때만 기록되므로 수집이 며칠 멈췄으면 이 시각도 그만큼 옛것이고, 적재기준시각과 벌어져 있으면 그 사이의 적재는 감사를 안 거쳤다.
         g.상세 AS 감사상세,  -- 위반한 게이트의 이름과 건수. NULL = 위반 없음 또는 기록 없음.
         (SELECT CASE WHEN COUNT(*) > 0 THEN '마지막 수집이 ' || group_concat(자료종류, '·') || ' 의 정리를 건너뛰었다 — 원천에서 사라진 자료가 남아 있을 수 있다.' END
            FROM 수집상태 WHERE 단계 = '정리' AND 상태 = '건너뜀') AS 경고  -- ⚠ **어느 부분이 옛 값인가**를 문장으로. NULL = 그런 부분 없음.
    FROM (SELECT 1)
    LEFT JOIN 수집상태 s ON s.자료종류 = '전체' AND s.단계 = '수집'
    LEFT JOIN 수집상태 g ON g.자료종류 = '전체' AND g.단계 = '감사';
```

표 10(데이터 8 + 운영 2), 뷰 4, 명시 인덱스 15(그중 `조문` 좌표는 UNIQUE). 옛 스키마 대비 표 −8, 뷰 −8.

### 코덱스 1차 리뷰(gpt-6-astra, 2026-09-12)에서 받아들여 DDL에 반영한 것

- 시행일자 주석이 법 전체의 효력으로 읽히던 것 → "가장 늦게 시행되는 조항의 시행일"로. 의율조문 머리의 행 단위 → 출처·쟁점·항호목 단위로.
- CHECK로 닫은 것: `전원합의체`·`부칙여부` IN (0,1), 헌재 본문 셋 중 하나는 NOT NULL, 시행예정 두 컬럼의 동반 NULL, 모든 `<표>ID`·`법령ID`에 NOT NULL(SQLite의 TEXT PRIMARY KEY는 NULL을 허용한다).
- `조문판단`에 `조 IS NOT NULL`, `조문판단수`는 `의율조문`이 아니라 `조문판단` 위에서 세어 목록과 수가 갈리지 않게. `신선도.감사통과`에 `상태='완료'` 조건. `적재기준시각`은 수집 실행 종료 행(`전체`·`수집`)에서.
- `인용판례.피인용종류` 신설(다형 참조 규칙 D11을 피인용 쪽에도). `조문(법령ID, 조, 가지)` UNIQUE(실측 중복 0). `판례(선고일자)` 단독 인덱스 복원. 자명한 NULL 설명은 표 머리의 "빈 컬럼은 원천이 주지 않은 것이다" 한 줄로 접고 질의를 바꾸는 NULL만 컬럼에 남김.
- 코덱스 리뷰는 같은 스레드로 다섯 차례 돌렸다(`.codex-runs/20260912-15*-law-schema-review-*`). 마지막 남은 지적 "철회의 목록 소속"은 위 A1 항목의 '없음'과 같은 자리라는 규칙으로 닫았고 그 뒤로는 다시 보내지 않았다 — 구현 P3에서 A1 테스트(철회 확정 → 정리 → 감사 순서)로 검증한다.
- 2차·3차 리뷰에서 닫은 것: 헌재 CHECK의 빈 문자열, 법령 실패 원장의 키를 법령ID로, A1을 합집합 등식으로(옛 판본 본문 + 새 판본 실패의 공존, 철회 복귀 대기), 정리·철회의 상태 전이를 완결 수신 조건으로, P4 기준선을 옛 원장에서 독립적으로 산출, 예정 전용 법령의 판본 선택 규칙 통일.
- 받아들이지 않은 것: `신선도` 머리와 감사통과 주석의 문장은 CONGRESS와 같은 문장이어야 한다는 계약(`260912_DB 재분할.md` A3)이 있어 그대로 둔다. 대신 `감사상세`의 내용을 게이트 번호가 아니라 이름으로 쓰게 수집기를 바꾼다(P2).

### 스키마 안에서 아직 확정하지 않은 것 (구현에서 실측으로 정한다)

- `수집상태`의 `기준선` 컬럼이 `prune.정리막는것`의 기준선 질의를 그대로 대신하는지. 대신하지 못하면 `키` 컬럼을 되살린다.

## 구현 계획

각 단계는 "완료 판정"을 갖는다. 3단계 이상 파일을 바꾸므로 구현 세션 첫 동작은 `ToolSearch("select:TaskCreate,TaskUpdate,TaskList")` 후 아래 단계를 트래커에 옮기는 것이다. 테스트는 단계마다 `tdd` 스킬을 열고 seam을 정한 뒤 쓴다. 각 단계가 닫히면 `codex` 스킬(gpt-6-astra, medium)로 리뷰를 받는다 — 질문 형식은 `260912_DB 재분할.md` D7과 같다("네 프레임 중 어느 것을 어느 줄이 어기는가, 줄 인용 필수. 없으면 없다고").

브랜치 `refactor/law-db-schema`, PR 제목 `refactor: LAW.db를 법률 체계 이해에 필요한 표만으로 재설계한다`.

### P1. 스키마 상수와 형식 테스트

- `Scripts/law/schema.py`: `SCHEMA`를 위 DDL로 교체. 파일 머리 docstring 유지. `# 성진:` 후보 10줄은 사라진 표·컬럼 것을 지우고 남는 것만 유지(헌재 병합사건 표·헌재 주문 항목 적재·조문 전문 FTS5 후보).
- `_테이블문`·`_구조`·`드리프트질의`는 그대로.
- 테스트: `tests/law/test_주석형식.py` 바이트 기준선을 새 `load.py schema` 출력으로 다시 잰다. 이어짐·⚠ 검사가 독립 `--` 줄만 보던 것을 인라인 `--` 주석까지 보도록 `_주석줄들()`을 넓힌다(새 DDL은 인라인 주석이 대부분이다). `test_열린_값_집합은…`(`SELECT DISTINCT 위임구분`)과 `test_수집실패_포인터…`(`수집실패의 자료종류='위임행정규칙'`)는 CHECK로 닫혔으므로 삭제. `tests/law/test_적재.py::Test스키마`·`TestCHECK`·`Test뷰`를 새 표·CHECK·뷰 넷에 맞춰 다시 쓴다.
- 완료 판정: `uv run --group test pytest -q tests/law/test_주석형식.py tests/law/test_law_주석수치.py tests/law/test_경고생존.py tests/law/test_law_스키마원자성.py tests/law/test_law_신선도.py` 초록. `load.py schema` 출력이 `sqlite_master`에 그대로 보존됨(`test_경고생존`).

### P2. 적재 경로(store·normalize·collectors)

- `store.py`: `본문테이블`을 `{법령: (법령, 법령ID, ((조문, 법령ID),)), 판례: (판례, 판례ID, ()), 헌재결정례: (…), 법령해석례: (…)}`로. `record_failure`·`철회기록`·`복귀지우기`가 `수집실패`의 새 컬럼(최초일시·최종일시·실패종류 CHECK)에 맞게. `메타쓰기`·`메타읽기`·`수집끝냈다`·`기준선기록`은 `수집상태` 한 표로 접는다(기준선은 컬럼).
- `normalize.py`: `날짜컬럼` 정본을 새 표·컬럼으로. `선고정규화` 삭제, `형식·전원합의체 분해` 함수 신설(입력: 판결유형 문자열. 규칙: '결정'→결정, '명령'→명령, '심판'→심판, 그 밖 '판결' 포함→판결, 못 나누면 NULL. '전원합의체' 포함→1).
- `collectors/statute.py`: 목록 두 개(현행+시행예정)를 법령ID로 묶어 한 행으로. 현행 판본이 여럿이면 시행일자가 가장 늦은 것, 예정 판본은 **시행일이 오늘 뒤인 것 중** 가장 이른 것을 `시행예정일련번호`·`시행예정일`에(실측: 시행예정 목록에 시행일이 이미 지난 판본이 102건 섞여 있다. 그것은 예정으로 잇지 않는다). 본문 파싱에서 부칙·조문요소 적재 제거, `조문내용` 제거, 제목 행을 `편장절` 경로로 접기. 접는 규칙: 순서대로 훑으며 `^제\d+(편|장|절|관)` 제목을 수준별 슬롯(편·장·절·관)에 넣고, 상위 수준이 갱신되면 하위 슬롯을 비운다. 그 밖의 제목 행(실측 44건, '제3속 …'·'○○법은 이를 폐지한다' 같은 것)은 가장 아래 슬롯 뒤에 그대로 덧붙인다. 경로는 채워진 슬롯을 ' > '로 잇는다. 단순 누적(group_concat)은 틀린다 — 실측에서 제1편 총칙이 제2편 조문에까지 따라붙었다.
- `collectors/precedent.py`: `형식`·`전원합의체` 적재, 원문 컬럼 제거, `참조조문`·`참조판례` 이름.
- `collectors/ruling.py`: 행정심판례 분기 삭제. 헌재 껍데기(전문·판시사항·결정요지 모두 빈 값)는 `저장` 대신 `record_failure(…, '본문없음')`. `주문재추출` 유지. 법령해석례 `등록일자`.
- `collectors/admrule.py` 삭제. `collectors/delegation.py`: 위임구분이 시행령·시행규칙인 잎만 남기고 `해결()`(행정규칙 ID 해결) 삭제. 완료 표지는 `법령.위임수집판본`(아래 위임 재개 항목).
- `collectors/run.py` `순서`에서 심판례·행정규칙 제거. 스키마 3단(`init_schema → 이행 → migrate`)에서 `이행` 호출 제거(P4에서 함수 자체가 사라진다). `_감사하고_남긴다`가 `수집상태('전체','감사', 상태='완료', 건수=위반 수, 상세=…)`를 쓰되 **상세는 게이트 번호가 아니라 게이트 이름으로** 쓴다(예: '적재 건수가 목록과 안 맞는 자료종류=1 · 재시도 실패 잔존=3'). `.schema`만 읽는 조회자가 'A1=3'을 복원할 수 없기 때문이다. 수집 실행이 끝날 때 `수집상태('전체','수집','완료', 갱신일시=now)`를 써서 `신선도.적재기준시각`의 근거로 삼는다.
- **키 계약(법령).** 저장 키·실패 원장 키·정리 키는 모두 `법령ID`이고, 원천과 주고받는 손잡이(본문 요청·목록 대조)만 MST다. 목록 단계가 두 목록(현행·시행예정)을 법령ID로 묶어 **선택 판본**(현행 중 시행일 최신 → 없으면 예정 중 시행일이 오늘 뒤인 것의 최소 → 그것도 없으면 예정 중 시행일 최신)과 **예정 판본**(선택 판본이 아닌 예정 중 시행일이 오늘 뒤인 것의 최소, 없으면 NULL)을 정한다. 이 규칙 하나를 목록 단계와 P4 변환이 함께 쓴다. 기수집 판정은 "법령ID 행이 있고 그 `법령일련번호`가 선택 판본 MST와 같다"이고, 다르면 본문을 다시 받아 행을 교체한다(REPLACE로 `조문`·`위임`은 CASCADE 삭제). 본문 실패는 `수집실패('법령', 자료ID=법령ID, 메시지에 MST)`이고 어느 MST든 성공하면 그 법령ID의 실패 행을 지운다. 새 판본 수신에 실패하면 옛 판본 행은 남기고 실패 행을 '재시도'로 적는다(둘이 공존할 수 있으므로 A1은 합이 아니라 합집합으로 센다. 아래 P3). 예정 두 컬럼은 예정 목록에 그 법령이 있으면 갱신하고, **예정 목록이 완결 수신일 때만** 없어진 예정을 NULL로 되돌린다(부분 수신은 취소로 읽지 않는다). 옛 `run._철회확정`도 법령ID로 부른다.
- **위임 재개.** `법령.위임수집판본`(TEXT)에 위임을 받은 시점의 MST를 적는다. NULL이거나 `법령일련번호`와 다르면 다시 받는다. `delegation._완료`는 응답의 MST가 현재 행의 `법령일련번호`와 같을 때만 쓴다. 이 컬럼이 `위임수집일시`를 대신한다(시각으로는 판본 교체를 사후 판별할 수 없다).
- **헌재 껍데기.** 판서는 `collectors/ruling.py`가 아니라 공통 `loop.수집루프`에 있다. 파서가 `본문없음` 표지를 돌려주면 루프가 `store.저장` 대신 `record_failure(…, '본문없음')`을 부르고, 다음 실행은 목록에 있어도 다시 묻지 않는다(재조회는 `--재조회 본문없음` 같은 명시 옵션으로만).
- **철회.** 옛 `원천철회일` 컬럼과 `store.철회된것`·`loop.py`의 복귀 경로(`원천철회일=NULL`)를 `수집실패('철회')`로 옮긴다. 정책을 바꾼다: 철회가 확정되면 한 트랜잭션에서 **본문 행과 파생 행(`의율조문`·`인용판례`의 그 자료 행, 다른 판단의 `피인용자료ID`가 이 자료를 가리키면 NULL)을 지우고** 실패 원장에 '철회'를 쓴다. 옛 설계는 행을 보존하고 뷰에 철회 표지를 붙였는데, 새 뷰에서 그 표지를 뺐으므로 보존하면 철회된 판단이 정상 판단처럼 보인다. 목록에 다시 나타나면 '철회' 행을 그대로 둔 채 본문을 다시 받고, **성공했을 때** 그 행을 지운다(재수신 실패·표본 밖이면 '철회'로 남아 있고 그것이 복귀 대기 상태다). `test_정리.py`의 복귀 케이스가 seam.
- **`refparser.py`의 삭제 컬럼 의존.** `법령사전`이 `현행연혁코드`로 현행을 골랐는데 이제 `법령` 전 행이 현행이다. `재파싱`의 "있는 조" 확인이 MST 조인이었는데 `조문(법령ID, 조, 가지)`로. `_ID컬럼`을 `<표>ID`로. `인용판례.피인용종류`는 파서가 피인용법원에서 정한다('헌법재판소'→헌재결정례, 그 밖의 법원→판례, 못 정하면 NULL이고 그때 `피인용자료ID`도 NULL). `prune`의 피인용 연결 해제는 `피인용종류`를 조건으로 쓴다.
- **`prune.py` 상태 전이.** 정리는 자료종류마다 키 단위로 한다(법령은 법령ID, 현행·예정 어느 목록에도 없을 때 누락). 완결 수신 목록에서만 상태를 바꾼다. 본문 행이 있는 자료가 목록에 없으면 `수집실패('목록누락', 시도횟수=연속 누락 수)`를 올리고 두 번 연속이면 본문·파생 행과 그 원장 행을 함께 지운다. 목록에 돌아오면 완결 수신일 때 그 행을 지우고, 부분 수신일 때는 시도횟수만 0으로 되돌려 둔다(옛 `복귀지우기` 계약 그대로. 부분 목록에서 지우면 A1 좌변이 기준선보다 커진다). 본문이 없는 '없음'·'재시도'·'본문없음'·'철회' 자료가 완결 목록에서 사라지면 원장 행을 지운다(부분 수신에서는 손대지 않는다). 그래서 완결 수신 뒤에는 '철회' 행이 전부 목록 안의 자료이고 A1이 목록 소속을 따로 묻지 않아도 된다. 시도횟수는 실패종류가 바뀔 때 1로 되돌린다. 기준선 보존 조건은 옛 그대로다: 완결 수신이고 급감 판정이 아닐 때만 `수집상태.기준선`을 덮으며, 법령의 기준선은 판본 수가 아니라 두 목록의 DISTINCT 법령ID 수다. 옛 `'부분수신'` 상태는 `'부분'`, 옛 `'복귀대기'` 행은 없앤다(복귀 대기는 위 철회 항목의 정의로 대신한다).
- `source.py` 봉투 표에서 행정심판례·행정규칙 제거. `source_fields.json`에서 해당 키 제거 후 `verify.py --기준선갱신`.

### P4. 변환 스크립트와 컷오버

- 일회성 `Scripts/law/convert_v3.py`(PEP 723): `ATTACH 'OLD' AS 옛;` 후 새 `init_schema`가 깐 빈 파일에 `INSERT INTO … SELECT …`. 규칙은 이 계획의 결정 대장 그대로다. 법령 한 행 병합은 P2 키 계약의 선택 판본·예정 판본 규칙을 그대로 쓴다(같은 함수를 변환 스크립트가 import한다), `위임수집판본`은 선택 판본 MST에 옛 `수집상태(법령, 위임, 그 MST)='완료'` 행이 있을 때만 그 MST이고 아니면 NULL(다른 판본의 완료 행은 쓰지 않는다), 위임 행도 선택 판본의 것만 옮긴다, 조문에서 제목 행을 편장절로 접는 윈도 질의, 판례 형식·전원합의체 유도, 헌재 껍데기 제외 + `수집실패('본문없음')`, 위임 시행령·시행규칙만, 의율조문 행심 제외·출처 이름 매핑, 수집실패에 옛 수집실패('없음'·'재시도'. 법령은 MST를 법령ID로 바꿔 적고 선택 판본이 담긴 법령ID의 실패는 버린다)+정리후보 중 본문 행이 살아남는 자료만('목록누락', 시도횟수=연속누락)+원천철회일 NOT NULL인 자료는 **본문을 담지 않고** '철회'로. 수집상태는 옛 행을 복사하지 않고 새로 쓴다: 자료종류마다 `목록`·`정리` 행을 '완료'로. **기준선은 변환 결과가 아니라 옛 원장에서 낸다** — 판례·헌재·해석례는 옛 `수집상태(종류,'목록','전체','완료')`의 건수 그대로(옛 A1이 통과했으므로 옛 본문+없음과 같다. 헌재는 껍데기가 '본문없음'으로 옮겨져 합집합 수가 유지된다), 법령은 옛 `법령` 표의 DISTINCT 법령ID 수(옛 법령 '없음' 실패는 MST뿐이라 법령ID를 모르므로 행도 옮기지 않고 기준선에도 넣지 않는다. 첫 일일 실행이 목록으로 다시 잡는다). 옛 판례·헌재·해석례 기준선이 옛 등식 `본문+없음 = 목록+계류+철회−복귀대기`로 맞았다면 새 등식도 맞는다 — 계류(정리후보)는 '목록누락'으로 빼고, 옛 철회 행은 본문을 빼고 '철회'로 옮긴다(옛 등식에서 목록 밖 철회는 우변에 더해져 있었으므로 변환 직후 A1은 그 수만큼 어긋날 수 있다. 지금 0건이라 변환 검증 기준은 '어긋남 = 옛 철회 중 목록 밖이던 수'이고, 첫 완결 수집이 정리로 맞춘다). 변환에서 본문을 빠뜨리면 이 기준선과 어긋나 A1이 빨개진다. `전체`·`수집` 행은 옛 메타의 마지막수집일시, `전체`·`감사` 행은 변환 직후 돌린 감사 결과. 변환 뒤 `refparser.재파싱`을 한 번 돌려 파생 표를 새 파서로 다시 만든다(옛 행을 옮기는 대신).
